# RISKS — риски, неизвестные и альтернативы

Оценки вероятности/влияния качественные: low / medium / high. Это не
формальная количественная оценка.

## 1. Ключевые риски

### R-01. Source2Viewer CLI меняет аргументы или формат вывода

**Вероятность:** medium. **Влияние:** high.
**Почему:** CLI прямо предупреждает, что аргументы не гарантируют стабильность.

**Митигация:**

- pin версии (20.1) и SHA-256 архива;
- wrapper с контрактными тестами;
- хранить raw stderr/exit code;
- fallback на C# VRF library/Package;
- не парсить человекочитаемый stdout там, где есть файлы.

**Триггер:** изменение вывода/exit codes после обновления.

### R-02. Collision export неполный или неверный

**Вероятность:** medium-high. **Влияние:** high.
**Почему:** `world_physics.vmdl_c` может не содержать все static props,
dynamic doors, breakables; VRF имеет ограничения по external meshes, spheres,
capsules.

**Митигация:**

- floor/wall/clearance тесты;
- сравнение с игровым поведением;
- material groups фильтровать осознанно;
- ручная проверка подозрительных мест;
- не использовать collision для выводов, пока тесты не пройдены.

**Триггер:** nav-связь проходит через стену; floor test < 95%.

### R-03. Nav — бот-абстракция, а не игрок

**Вероятность:** high. **Влияние:** high.
**Почему:** nav generated for radius 16/height 71; могут отсутствовать
boost-позиции, узкие проходы, часть прыжков; crouch areas отдельные.

**Митигация:**

- не считать nav истиной о проходимости;
- collision-проверки и ручные контрольные точки;
- маркировать маршруты «nav-only»;
- измерять реальные маршруты в игре;
- хранить one-way/аномалии.

**Триггер:** игрок проходит там, где nav не даёт связи, или наоборот.

### R-04. One-way, drops и вертикальные аномалии

**Вероятность:** high. **Влияние:** medium-high.
**Почему:** 175 one-way связей на Dust2; 3 вертикальные аномалии; drops
влияют на forward/reverse.

**Митигация:**

- направленный граф;
- отдельная классификация walk/jump/drop/ladder;
- проверка generation limits;
- collision/visual проверка аномалий;
- не усреднять forward/reverse.

**Триггер:** обратный маршрут сильно длиннее без объяснения.

### R-05. Глобальные параметры движения неизвестны

**Вероятность:** medium (снижена после измерений 2026-10-19). **Влияние:** high.
**Почему:** исходно в конфигах не было `sv_accelerate`/`sv_friction`;
community-значения не подтверждены.

**Статус 2026-11:** convars и установившиеся скорости измерены на локальном
listen server указанной сборки; см. [MOVEMENT.md](MOVEMENT.md). Остаточный риск —
одиночные прогоны, отсутствие demo-tick калибровки и возможные изменения CS2.

**Митигация:**

- повторная серия измерений по demo ticks;
- использовать `m_flMaxSpeed` из `weapons.vdata_c` как проверяемую базу;
- bootstrap/чувствительность;
- не выдавать время как измеренное до калибровки.

**Триггер:** расхождение модели и новых измерений > 10%.

### R-06. Симуляция 5v5 недоопределена

**Вероятность:** high. **Влияние:** high.
**Почему:** выбор маршрута, блокировки, поведение, spawn assignment, решения
игроков не следуют из геометрии.

**Митигация:**

- начать с чистой симуляции времени;
- явные сценарии/допущения;
- Monte Carlo и sensitivity;
- не выдавать исход раунда;
- сравнивать с демками.

**Триггер:** результат сильно зависит от seed/выбора маршрута без объяснения.

### R-07. Ложная точность баланса

**Вероятность:** high. **Влияние:** high.
**Почему:** расстояние ≠ время; один короткий маршрут ≠ преимущество; спавны
не равновероятны.

**Митигация:**

- distance-first + ideal straight-line time в MVP;
- CI/распределения;
- несколько метрик;
- явные ограничения;
- не сводить к одному score.

**Триггер:** вывод «карта сбалансирована/несбалансирована» по одному числу.

### R-08. Обновление CS2 ломает данные

**Вероятность:** medium. **Влияние:** medium-high.
**Почему:** nav version/layout, map VPK, collision, weapon speeds меняются.

**Митигация:**

- manifest с ClientVersion/buildid/hashes;
- regression diff;
- fail при неизвестной версии;
- не обновлять golden автоматически.

**Триггер:** изменился area_count/hash/route.

### R-09. Большие collision-файлы и память

**Вероятность:** medium. **Влияние:** medium.
**Почему:** Dust2 21.8 МБ, Inferno 61.3 МБ; triangles + BVH могут занимать
сотни МБ.

**Митигация:**

- offline ingest;
- decimation только для LOS, не для walkability;
- потоковая загрузка;
- NumPy/C#/Rust при необходимости;
- кэш BVH.

**Триггер:** OOM/время загрузки > допустимого.

### R-10. Multi-level и несколько компонент

**Вероятность:** high. **Влияние:** medium.
**Почему:** Nuke/Vertigo/Train; 2–3 undirected components на многих картах.

**Митигация:**

- учитывать z при point location;
- не предполагать одну компоненту;
- проверять спавны/bombsite в main component;
- визуализация по слоям.

**Триггер:** маршрут «телепортируется» между этажами.

### R-11. Windows `Test-Path`

**Вероятность:** medium. **Влияние:** medium.
**Почему:** известная проблема окружения.

**Митигация:** запрет неквалифицированного `Test-Path`; .NET/Python API;
проверка сторонних скриптов.

**Триггер:** окно «Выберите приложение» или ошибка парсинга.

### R-12. Лицензии и публикация данных

**Вероятность:** medium. **Влияние:** high (юридическое/репутационное).
**Почему:** игровые ассеты принадлежат Valve; MIT инструментов не покрывает
ассеты.

**Митигация:** не коммитить/не публиковать ресурсы; только агрегированные
метрики; attribution инструментов; отдельное согласование публикации.

**Триггер:** запрос на публикацию VPK/nav/glTF.

### R-13. Scope creep

**Вероятность:** high. **Влияние:** high.
**Почему:** легко уйти в 3D-движок, combat, ML.

**Митигация:** этапы и acceptance criteria; core/extensions/research;
запрет на combat до валидации базы.

**Триггер:** новые функции без работающего MVP.

### R-14. Один map overfitting

**Вероятность:** high. **Влияние:** medium.
**Почему:** Dust2 выбран первым; разные карты имеют разные nav params,
ladders, components.

**Митигация:** этап multi-map; не обобщать Dust2 на все карты; проверять
ladders на Train/Mirage.

**Триггер:** модель ломается на второй карте.

### R-15. Автоопределение спавна/этажа может ошибаться

**Вероятность:** medium. **Влияние:** medium.

**Почему:** multi-level карты, нестандартные spawn-наборы, изменение карты.

**Митигация:**

- `find_area_verbose` + `ambiguous` flag;
- validation auto-detect на всех спавнах;
- backlog: manual spawn override в `config/spawn_overrides/<map>.json`;
- override не изменяет исходные ресурсы;
- в отчётах помечать, что spawn исправлен вручную.

**Триггер:** spawn попадает не на тот этаж/область.

### R-16. Динамические объекты и состояние раунда

**Вероятность:** medium. **Влияние:** medium.
**Почему:** двери, стекло, breakables, smoke/molotov меняют проходимость.

**Митигация:** MVP — статическая карта; динамика — отдельный слой; не
смешивать с nav.

**Триггер:** результаты расходятся из-за двери/стекла.

## 2. Неизвестные

1. Включает ли `world_physics.vmdl_c` collision всех static props?
2. Как именно CS2 назначает 5 спавнов из 15 при `mp_randomspawn 0`?
3. Какие значения `sv_accelerate`, `sv_friction`, `sv_stopspeed`,
   `sv_maxspeed`, jump impulse в текущей CS2?
4. Как nav обрабатывает crouch/jump/boost и насколько расходится с игроком?
5. Есть ли в nav place names на других картах (Dust2 — пусто)?
6. Насколько Awpy/VRF совпадают с нашим parser на всех картах?
7. Можно ли использовать `world_physics` для walkability без фильтрации
   player clips?
8. Как меняется nav при обновлениях и как часто?
9. Есть ли легальный/технический способ получить collision без запуска
   Source2Viewer (например, C# library)?
10. Как валидировать маршруты по реальным демкам без утечки данных?

## 3. Альтернативы

### A. Только nav

**Плюсы:** быстро, уже работает.
**Минусы:** нет collision/vis, ложные проходы.
**Когда:** MVP маршрутов и расстояний.

### B. Nav + collision

**Плюсы:** проверка пола/стен/clearance, выше достоверность.
**Минусы:** тяжёлый импорт, фильтрация, сложность.
**Когда:** обязательное ядро после MVP.

### C. Полная геометрия + физика

**Плюсы:** максимальная точность.
**Минусы:** огромная стоимость, не нужна для баланса маршрутов.
**Когда:** research, не MVP.

### D. Demo-driven validation

**Плюсы:** реальные траектории/время.
**Минусы:** нет ground truth по альтернативам; демки могут быть старые.
**Когда:** валидация движения/маршрутов.

### E. Ручная разметка контрольных точек

**Плюсы:** быстро, понятно.
**Минусы:** субъективно, не масштабируется.
**Когда:** калибровка и проверка.

## 4. Что может сорвать проект

Наиболее опасные комбинации:

1. Collision export окажется неполным/непригодным + nav слишком грубый →
   нельзя доверять проходимости.
2. Не удастся измерить движение/время → останутся только расстояния.
3. Симуляция 5v5 окажется недоопределённой → выводы о балансе будут
   спекулятивными.
4. Scope creep в combat/3D → MVP не будет закончен.
5. Обновления CS2 будут ломать формат чаще, чем успеем поддерживать.

**Вывод:** проект реализуем как **инструмент анализа маршрутов и геометрии**.
Как **точный предиктор соревновательного баланса** — нет, без модели
движения, поведения и валидации на демках.
